CompiladoresLab - AST Completa e Erros Sintáticos Comuns no Slang

Introdução12.1

No capítulo anterior, o parser já passou a reconhecer expressões do Slang e a construir uma AST para esse subconjunto da linguagem. Isso resolve a base da precedência de operadores, mas ainda não representa o programa inteiro.

Agora vamos dar o próximo passo natural. Em vez de construir árvores apenas para expressões, você vai organizar uma AST para as principais construções da linguagem:

  • declarações de variável;
  • blocos;
  • condicionais if e else;
  • laços loop;
  • break, continue e return;
  • funções e listas de parâmetros;
  • chamadas de função.

Além disso, vamos melhorar algumas mensagens de erro sintático que costumam aparecer com frequência quando o parser ainda está em construção.

Da árvore de expressões para a árvore do programa12.2

Quando você parseia apenas uma expressão, a raiz da AST costuma ser um operador, um literal ou um agrupamento. Mas um programa real não é só isso. Ele é uma sequência de declarações e comandos.

Por exemplo, este trecho:

fn main(args: void) -> void {
    x: int = 10
    if x > 0 {
        print(x)
    } else {
        return
    }
}

não deve virar apenas uma árvore de operadores. Ele precisa virar uma árvore sintática que represente:

  • uma função;
  • um bloco como corpo;
  • uma declaração de variável;
  • um comando if;
  • uma chamada de função;
  • um return.

A gramática estrutural do Slang12.3

Para organizar essa etapa, vamos usar uma gramática de alto nível para o programa.

$$ \begin{split} Program &\to Declaration^*\ EOF \\ Declaration &\to FunctionDecl \mid VarDecl \mid Statement \\ FunctionDecl &\to \texttt{fn}\ id\ (Params)\ \texttt{->}\ Type\ Block \\ VarDecl &\to id\ \texttt{:}\ Type\ \texttt{=}\ Expression \\ Statement &\to IfStmt \mid LoopStmt \mid BreakStmt \mid ContinueStmt \mid ReturnStmt \mid Block \mid Expression \\ Block &\to \{\ Declaration^*\ \} \\ IfStmt &\to \texttt{if}\ Expression\ Block\ ElsePart \\ ElsePart &\to \texttt{else}\ Block \mid \epsilon \\ LoopStmt &\to \texttt{loop}\ Expression\ Block \\ BreakStmt &\to \texttt{break} \\ ContinueStmt &\to \texttt{continue} \\ ReturnStmt &\to \texttt{return}\ Expression \mid \texttt{return} \end{split} $$

Essa não é a única forma possível de organizar a gramática, mas ela já é suficiente para estruturar a AST da linguagem de maneira coerente.

Uma AST mais completa12.4

Agora precisamos abandonar a AST minimalista de expressões e passar a uma árvore com nós para programa, comandos e declarações.

Estrutura geral12.4.1

Uma forma prática de fazer isso em C é usar:

  • um enum com todos os tipos de nó;
  • uma struct AstNode com union;
  • uma estrutura auxiliar de lista encadeada para armazenar sequências de filhos.

Criando include/compiler/ast.h12.4.2

Substitua include/compiler/ast.h por uma versão mais completa:

#ifndef COMPILER_AST_H_
#define COMPILER_AST_H_

#include <stdbool.h>
#include "compiler/token.h"

typedef enum {
    AST_PROGRAM,
    AST_FUNCTION,
    AST_PARAM,
    AST_VAR_DECL,
    AST_BLOCK,
    AST_IF,
    AST_LOOP,
    AST_BREAK,
    AST_CONTINUE,
    AST_RETURN,
    AST_EXPR_STMT,
    AST_ASSIGN,
    AST_BINARY,
    AST_UNARY,
    AST_CALL,
    AST_LITERAL,
    AST_VARIABLE,
    AST_GROUPING,
    AST_TYPE
} AstNodeType;

typedef struct AstNode AstNode;

typedef struct AstNodeList {
    AstNode *node;
    struct AstNodeList *next;
} AstNodeList;

struct AstNode {
    AstNodeType type;

    union {
        struct {
            AstNodeList *declarations;
        } program;

        struct {
            Token name;
            AstNodeList *params;
            AstNode *return_type;
            AstNode *body;
        } function;

        struct {
            Token name;
            AstNode *param_type;
        } param;

        struct {
            Token name;
            AstNode *decl_type;
            AstNode *initializer;
        } var_decl;

        struct {
            AstNodeList *statements;
        } block;

        struct {
            AstNode *condition;
            AstNode *then_branch;
            AstNode *else_branch;
        } if_stmt;

        struct {
            AstNode *condition;
            AstNode *body;
        } loop_stmt;

        struct {
            AstNode *value;
        } return_stmt;

        struct {
            AstNode *expression;
        } expr_stmt;

        struct {
            Token name;
            AstNode *value;
        } assign;

        struct {
            Token operator;
            AstNode *left;
            AstNode *right;
        } binary;

        struct {
            Token operator;
            AstNode *operand;
        } unary;

        struct {
            AstNode *callee;
            AstNodeList *arguments;
        } call;

        struct {
            Token value;
        } literal;

        struct {
            Token name;
        } variable;

        struct {
            AstNode *expression;
        } grouping;

        struct {
            Token name;
        } type_name;
    } as;
};

AstNodeList *ast_list_append(AstNodeList *list, AstNode *node);

AstNode *ast_make_program(AstNodeList *declarations);
AstNode *ast_make_function(Token name, AstNodeList *params, AstNode *return_type, AstNode *body);
AstNode *ast_make_param(Token name, AstNode *param_type);
AstNode *ast_make_var_decl(Token name, AstNode *decl_type, AstNode *initializer);
AstNode *ast_make_block(AstNodeList *statements);
AstNode *ast_make_if(AstNode *condition, AstNode *then_branch, AstNode *else_branch);
AstNode *ast_make_loop(AstNode *condition, AstNode *body);
AstNode *ast_make_break(void);
AstNode *ast_make_continue(void);
AstNode *ast_make_return(AstNode *value);
AstNode *ast_make_expr_stmt(AstNode *expression);
AstNode *ast_make_assign(Token name, AstNode *value);
AstNode *ast_make_binary(Token operator, AstNode *left, AstNode *right);
AstNode *ast_make_unary(Token operator, AstNode *operand);
AstNode *ast_make_call(AstNode *callee, AstNodeList *arguments);
AstNode *ast_make_literal(Token value);
AstNode *ast_make_variable(Token name);
AstNode *ast_make_grouping(AstNode *expression);
AstNode *ast_make_type(Token name);

void ast_print(const AstNode *node);
void ast_free(AstNode *node);

#endif

O que essa estrutura resolve12.4.3

Com essa versão, a árvore deixa de representar apenas expressões e passa a representar um programa inteiro. Isso é importante porque as próximas fases do compilador, como análise semântica e geração de código, normalmente trabalham sobre essa visão mais ampla da estrutura.

Implementando os construtores da AST12.5

O arquivo src/compiler/ast.c vai crescer bastante, mas o padrão continua o mesmo. Você aloca um nó, preenche o tipo e grava os campos da união correspondente.

Em vez de repetir aqui centenas de linhas quase idênticas de construtores, vale organizar o arquivo em três grupos:

  • helpers de alocação e listas;
  • construtores de declarações e comandos;
  • construtores de expressões e impressão da árvore.

O helper de lista pode ser implementado assim:

AstNodeList *ast_list_append(AstNodeList *list, AstNode *node) {
    AstNodeList *item = (AstNodeList *)malloc(sizeof(AstNodeList));
    if (item == NULL) {
        fprintf(stderr, "Erro: memória insuficiente para lista da AST.\n");
        exit(74);
    }

    item->node = node;
    item->next = NULL;

    if (list == NULL) return item;

    AstNodeList *current = list;
    while (current->next != NULL) current = current->next;
    current->next = item;
    return list;
}

Um construtor de declaração de variável, por exemplo, segue o mesmo modelo dos nós da aula anterior:

AstNode *ast_make_var_decl(Token name, AstNode *decl_type, AstNode *initializer) {
    AstNode *node = ast_allocate();
    node->type = AST_VAR_DECL;
    node->as.var_decl.name = name;
    node->as.var_decl.decl_type = decl_type;
    node->as.var_decl.initializer = initializer;
    return node;
}

O mesmo vale para AST_FUNCTION, AST_IF, AST_LOOP, AST_RETURN, AST_CALL e os demais.

Imprimindo a árvore completa12.6

Quando a AST deixa de ser apenas uma expressão, a impressão precisa deixar mais claro que tipo de nó você está vendo. Um programa completo pode ser mostrado com rótulos como:

program
├── fn(main)
│   ├── params
│   ├── type(void)
│   └── block
│       ├── var_decl(x)
│       │   ├── type(int)
│       │   └── num(10)
│       └── if
│           ├── >
│           │   ├── id(x)
│           │   └── num(0)
│           ├── block
│           │   └── call
│           │       ├── id(print)
│           │       └── args
│           │           └── id(x)
│           └── block
│               └── return

Esse tipo de impressão é especialmente útil para depurar problemas de associação estrutural entre comandos e expressões.

Ajustando o parser para produzir a AST completa12.7

Agora o parser precisa deixar de retornar apenas uma expressão e passar a retornar um programa.

Nova função inicial12.7.1

Em vez de começar em parse_expression, a entrada principal passa a ser algo como:

static AstNode *parse_program(Parser *parser) {
    AstNodeList *declarations = NULL;

    while (!check(parser, TOK_EOF)) {
        declarations = ast_list_append(declarations, parse_declaration(parser));
    }

    return ast_make_program(declarations);
}

Separando declaração e comando12.7.2

Essa divisão é importante porque nem tudo no topo do programa é um simples comando.

static AstNode *parse_declaration(Parser *parser) {
    if (match(parser, TOK_KW_FN)) return parse_function_decl(parser);

    if (check(parser, TOK_IDENTIFIER) && parser_next_starts_var_decl(parser)) {
        return parse_var_decl(parser);
    }

    return parse_statement(parser);
}

Esse parser_next_starts_var_decl pode ser implementado com uma forma de lookahead ou com uma organização diferente da estrutura do parser. O importante aqui é a ideia. Uma declaração de variável começa com id :, enquanto uma atribuição ou expressão simples começa de outro jeito.

Mensagens de erro mais comuns12.8

Quando o parser começa a crescer, as mensagens de erro deixam de ser um detalhe. Elas passam a ser uma ferramenta essencial de depuração.

Aqui estão alguns erros frequentes que vale tratar explicitamente.

Falta de )12.8.1

[linha 4] Erro sintático próximo de "{": Esperado ')' após a expressão.

Esse erro aparece muito em condições de if, chamadas de função e agrupamentos.

Falta de } ao final de bloco12.8.2

[linha 12] Erro sintático próximo de "else": Esperado '}' fechando o bloco.

Esse é um dos erros mais comuns quando o corpo de if, loop ou fn está sendo escrito.

Declaração de variável sem tipo12.8.3

[linha 3] Erro sintático próximo de "=": Esperado ':' após o nome da variável.

ou:

[linha 3] Erro sintático próximo de "=": Esperado um tipo após ':'.

Atribuição sem expressão à direita12.8.4

[linha 7] Erro sintático próximo de "}": Esperado uma expressão após '='.

return incompleto em contexto inadequado12.8.5

[linha 15] Erro sintático próximo de "}": Esperado expressão após 'return'.

se a gramática exigir retorno com valor naquele caso.

Chamada de função com vírgula sobrando12.8.6

[linha 9] Erro sintático próximo de ")": Esperado argumento após ','.

Como escrever essas mensagens no parser12.8.7

Sempre que possível, associe a mensagem a um ponto sintático preciso.

consume(parser, TOK_RBRACE, "Esperado '}' fechando o bloco.");
consume(parser, TOK_COLON, "Esperado ':' após o nome da variável.");
consume(parser, TOK_RPAREN, "Esperado ')' após a lista de argumentos.");

Isso costuma ser muito mais útil do que uma mensagem genérica como "Erro de sintaxe".

O que muda na prática ao final desta etapa12.9

Depois dessa expansão, o compilador passa a ter uma visão estrutural muito mais rica do programa. Ele já não enxerga apenas uma expressão isolada. Ele passa a distinguir:

  • o que é declaração;
  • o que é comando;
  • o que é bloco;
  • o que é função;
  • o que é chamada;
  • o que é expressão interna de cada construção.

É essa árvore maior que permitirá implementar depois checagem de tipos, análise de escopo, validação de return, uso correto de break e continue, além da própria geração de código.

Próximos Passos12.10

Com a AST completa em mãos e com mensagens de erro sintático mais úteis, o próximo avanço natural é a análise semântica. A partir daí, o compilador deixa de perguntar apenas se a estrutura é válida e passa a perguntar também se ela faz sentido dentro das regras da linguagem.
