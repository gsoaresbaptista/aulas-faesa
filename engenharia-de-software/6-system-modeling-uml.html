Engenharia de Software Modelagem de Sistemas com UML

Introdução à Modelagem de Sistemas6.1

A modelagem de sistemas é o processo fundamental de desenvolver modelos abstratos de um sistema, onde cada modelo apresenta uma visão ou perspectiva diferente desse sistema. Segundo a visão clássica de Ian Sommerville em sua 9ª edição, a modelagem serve como uma ponte entre a especificação de requisitos e o projeto de software. Ela nos permite representar o sistema de uma maneira que seja compreensível tanto para os desenvolvedores quanto para os interessados (stakeholders), abstraindo detalhes irrelevantes da implementação para focar na essência do que o sistema deve ser e como ele deve se comportar.

É importante compreender que um modelo não é o sistema em si, mas uma simplificação da realidade. Utilizamos a modelagem para gerenciar a complexidade, permitindo que a equipe visualize a infraestrutura do sistema, as interações entre os componentes e as interfaces com o ambiente externo antes que o código comece a ser escrito. Na prática da Engenharia de Software moderna, a Unified Modeling Language (UML) tornou-se o padrão de facto para essas representações, oferecendo um vocabulário gráfico rico que abrange desde a visão externa do usuário até a estrutura interna dos dados.

Para orientar nosso estudo, dividiremos a modelagem em quatro perspectivas essenciais: a perspectiva externa, que define o contexto e os limites do sistema; a perspectiva de interação, que descreve como o sistema interage com usuários e outros sistemas; a perspectiva estrutural, que foca na organização dos dados e componentes; e a perspectiva comportamental, que detalha como o sistema reage a eventos e processos ao longo do tempo.

O Caso Base: Pet Shop "Amigo Fiel"6.2

Para que possamos aplicar esses conceitos de forma prática e imediata, utilizaremos como fio condutor o desenvolvimento do sistema para o Pet Shop "Amigo Fiel". Este estabelecimento oferece serviços de banho e tosa, consultas veterinárias e venda de produtos especializados. O proprietário deseja automatizar o agendamento de serviços, o controle de estoque e o histórico de atendimento dos pets.

Atualmente, o processo é manual e gera confusão. Clientes ligam para agendar horários, funcionários anotam em agendas de papel e nem sempre sabem se há produtos disponíveis para os procedimentos. O novo sistema deve permitir que o recepcionista cadastre clientes e seus animais, realize agendamentos vinculando-os a um funcionário específico e registre a finalização do serviço para fins de cobrança. Ao longo desta aula, construiremos a modelagem deste sistema passo a passo, aplicando as perspectivas de Sommerville.

Perspectiva Externa: Modelos de Contexto6.3

A perspectiva externa preocupa-se com o ambiente em que o sistema operará. O primeiro passo da modelagem é definir os limites do sistema: o que faz parte dele e o que é externo a ele. Modelos de contexto ajudam a decidir quais funcionalidades devem ser implementadas e quais dependem de serviços externos. Muitas vezes, o contexto social e organizacional é tão importante quanto o contexto técnico, pois o sistema precisa se encaixar nos processos de trabalho existentes na empresa.

Para representar como o sistema se integra aos processos de negócio, utilizamos frequentemente o Diagrama de Atividades. Este diagrama foca no fluxo de dados ou de controle em um processo, sendo excelente para mostrar a sequência de passos necessária para atingir um objetivo organizacional. No contexto do Pet Shop, precisamos entender como um animal é recebido para um serviço.

Diagrama de Atividades e sua Simbologia6.3.0.1

Para ler corretamente um diagrama de atividades, você deve identificar os seguintes elementos gráficos padrão:

  • Círculo Sólido: Representa o Início do processo.
  • Retângulos de Cantos Arredondados: Representam as Atividades ou ações executadas.
  • Losangos (Diamantes): Representam Pontos de Decisão, onde o fluxo se divide baseando-se em uma condição (guard).
  • Seta: Indica a direção do Fluxo de Controle.
  • Círculo com Borda (Bullseye): Representa o Fim do processo.

Perspectiva de Interação: Casos de Uso e Sequência6.4

Uma vez definido o contexto, precisamos detalhar como o sistema interage com seus usuários e com outros sistemas. A modelagem de interação ajuda a identificar requisitos funcionais e a entender como as mensagens trafegam entre os agentes. Sommerville destaca que esta perspectiva é vital para projetar interfaces de usuário e protocolos de comunicação eficientes.

O Diagrama de Casos de Uso é a ferramenta principal aqui. Ele descreve as funções que o sistema fornece para os atores externos (usuários humanos ou sistemas). Cada "Caso de Uso" representa uma funcionalidade discreta que entrega um valor ao ator. É importante não confundir casos de uso com passos individuais de um algoritmo; eles devem ser vistos como metas completas do usuário.

Diagramas de Caso de Uso e sua Simbologia6.4.0.1

A notação gráfica destes diagramas é simplificada para facilitar a comunicação com o cliente:

  • Boneco de Palito (Stickman): Representa o Ator, que é qualquer entidade externa (humano ou sistema) que interage com o software.
  • Elipse: Representa o Caso de Uso, ou seja, a funcionalidade ou serviço oferecido pelo sistema.
  • Linha Sólida: Representa a Associação entre o ator e o caso de uso.
  • Retângulo (Fronteira): Opcionalmente, delimita os limites do sistema, separando o que está "dentro" do que é "externo".
  • Seta tracejada (<>/<>): Representa relacionamentos entre casos de uso. O include indica que uma funcionalidade é obrigatoriamente parte de outra.

Após identificar o que o sistema faz, o Diagrama de Sequência nos mostra como os objetos internos colaboram para realizar esse caso de uso ao longo do tempo. Ele é lido de cima para baixo e destaca a troca de mensagens entre atores e objetos do sistema.

Diagramas de Sequência e sua Simbologia6.4.0.2

Este diagrama introduz a dimensão temporal na modelagem:

  • Retângulos no Topo: Representam as Instâncias de Objetos ou atores participantes da interação.
  • Linha Tracejada Vertical: É a Linha de Vida (Lifeline), representando a existência do objeto durante o tempo da interação.
  • Retângulo Estrito sobre a Linha de Vida: Chamado de Barra de Ativação, indica quando o objeto está executando uma operação ou esperando uma resposta.
  • Seta Sólida: Representa uma Chamada Síncrona (o remetente espera pela resposta).
  • Seta Tracejada: Representa o Retorno da mensagem ou resposta.

Perspectiva Estrutural: Modelos de Classe6.5

A perspectiva estrutural descreve a organização do sistema em termos dos componentes que o compõem e seus relacionamentos. Diferente da perspectiva de interação, que é dinâmica, a estrutural é estática: ela define o "esqueleto" do software. O modelo mais comum nesta categoria é o Diagrama de Classes.

Diagramas de Classe e sua Simbologia6.5.0.1

Aqui, os símbolos são mais técnicos e detalhados:

  • Retângulo Dividido em 3 Partes: Representa a Classe. A parte superior contém o nome, a do meio os atributos (dados) e a inferior os métodos (comportamento).
  • Prefixos (+, -, #): Indicam a Visibilidade (+ público, - privado, # protegido).
  • Linha Sólida: Representa uma Associação genérica entre classes.
  • Setas de Cabeça Oca: Representam Herança ou Generalização.
  • Losangos na Ponta da Linha: Representam Agregação (losango vazio) ou Composição (losango preenchido).

Em um diagrama de classes, representamos as entidades do domínio, seus atributos (dados) e métodos (operações), além das associações entre elas (como elas se conhecem). Sommerville enfatiza a importância de entender as relações de generalização (herança) e agregação para criar sistemas modulares e reutilizáveis. No nosso Pet Shop, precisamos gerenciar Pets, mas alguns Pets podem ter características específicas se pensarmos em espécies diferentes ou necessidades especiais.

Cardinalidade (Multiplicidade)6.6

Um dos pontos mais críticos na modelagem estrutural é a definição da Cardinalidade (ou multiplicidade), que indica quantos objetos de uma classe podem estar associados a quantos objetos de outra. Sommerville destaca que a precisão aqui é fundamental para o projeto do banco de dados e para a implementação da lógica de coleções no código.

Notação Significado Exemplo no Pet Shop
1 Exatamente um Cada Pet possui exatamente 1 Dono (simplificando para o sistema).
0..* Zero ou muitos Um Cliente pode possuir 0 ou vários Pets cadastrados.
1..* Um ou muitos Um Agendamento deve ter pelo menos 1 Serviço vinculado.
0..1 Zero ou um Um Pet pode (ou não) ter 1 Coleira Eletrônica vinculada.

Do Diagrama para o Código (C++)6.7

Para que o modelo deixe de ser apenas um desenho e se torne software, precisamos traduzir as associações e cardinalidades para construções da linguagem. Em C++, associações "para muitos" (como de Cliente para Pet) são geralmente implementadas usando containers da STL, como std::vector.

Prática: Implementação em C++

Abaixo, mostramos como a relação 1:N entre Cliente e Pet é codificada. Observe o uso de ponteiros e coleções para manter a integridade do modelo.

#include <iostream>
#include <vector>
#include <string>

class Pet {
public:
    std::string nome;
    Pet(std::string n) : nome(n) {}
};

class Cliente {
private:
    std::string nome;
    // Tradução da cardinalidade 0..* (lista de pets)
    std::vector<Pet*> meusPets; 

public:
    Cliente(std::string n) : nome(n) {}
    
    void adicionarPet(Pet* p) {
        meusPets.push_back(p);
    }

    void listarPets() {
        std::cout << "Cliente: " << nome << "\n";
        for (auto p : meusPets) {
            std::cout << "- Pet: " << p->nome << "\n";
        }
    }
};

Do Código para o Diagrama (Engenharia Reversa)6.8

Muitas vezes, você receberá um código legado e precisará documentá-lo. A capacidade de "ler" o código e abstrair um diagrama é essencial. Considere o seguinte trecho:

class Servico {
    float valor;
};

class OrdemServico {
    Cliente* solicitante;
    std::vector<Servico> itens;
};

Ao analisar esse código, o engenheiro de software identifica imediatamente:

  1. Uma associação de 1 para 1 entre OrdemServico e Cliente (um ponteiro simples).
  2. Uma composição ou agregação de 1 para muitos entre OrdemServico e Servico (um vector).

Perspectiva Comportamental: Modelos de Estado6.9

Por fim, a perspectiva comportamental descreve o que acontece ou o que deveria acontecer quando o sistema recebe um estímulo externo. Enquanto o diagrama de sequência mostra o comportamento de uma interação específica, os modelos comportamentais mostram como o sistema, ou um objeto dele, reage ao longo de todo o seu ciclo de vida.

O Diagrama de Estados (Statecharts) é ideal para modelar objetos que mudam seu comportamento dependendo do que aconteceu com eles anteriormente. No "Amigo Fiel", o objeto "Agendamento" possui um ciclo de vida claro. Ele não pode ser "Finalizado" se ainda não foi "Iniciado", por exemplo. Modelar esses estados evita bugs lógicos onde o usuário tenta realizar ações em momentos errados.

Diagramas de Estado e sua Simbologia6.9.0.1

Este diagrama foca na evolução interna de um único objeto:

  • Círculo Sólido Preto: Representa o Estado Inicial.
  • Retângulos de Cantos Arredondados: Representam os Estados possíveis do objeto (ex: "Em Aberto", "Cancelado").
  • Setas: Representam as Transições, ou seja, a mudança de um estado para outro.
  • Rótulo na Seta: Descreve o Evento ou estímulo que causou a transição (ex: "Receber Pagamento").
  • Círculo com Borda: Representa o Estado Final ou encerramento do ciclo de vida daquele objeto.

Engenharia Dirigida a Modelos (MDE)6.10

Para encerrar a base conceitual, Sommerville introduz a Engenharia Dirigida a Modelos (Model-Driven Engineering - MDE). Esta é uma abordagem onde, em vez de focar no código-fonte, os desenvolvedores focam na criação de modelos de alto nível. Ferramentas automatizadas são então usadas para traduzir esses modelos em código executável.

Embora ainda não seja a norma em todos os setores devido à complexidade das ferramentas, a abordagem MDA (Model-Driven Architecture) propõe três níveis de abstração:

  1. CIM (Computation Independent Model): Focado apenas nos requisitos de negócio.
  2. PIM (Platform Independent Model): Descreve o sistema sem detalhes de plataforma (ex: sem saber se é Java ou C#).
  3. PSM (Platform Specific Model): Onde o modelo é refinado para uma tecnologia específica.

A grande vantagem prometida pela MDE é que, se a tecnologia mudar (ex: migrar de um servidor local para a nuvem), você só precisa atualizar o PSM, mantendo toda a lógica de negócio intacta no PIM.

  6. Discuta as vantagens e desvantagens de adotar a Engenharia Dirigida a Modelos (MDE) em um projeto de pequeno porte como o do Pet Shop "Amigo Fiel".
