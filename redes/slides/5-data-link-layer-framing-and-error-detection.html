Camada de Enlace, Enquadramento e Detecção de Erros

Professor: Gabriel Soares Baptista

Do problema à solução

A camada física entrega apenas um fluxo bruto de bits.

Isso cria três perguntas imediatas:

  • onde uma mensagem começa?
  • onde ela termina?
  • como saber se ela chegou correta?
Ideia central

A camada de enlace transforma bits em quadros, detecta erros e coordena a comunicação local.

Onde a camada de enlace fica

Dilema de projeto

Mais controle aumenta a confiabilidade, mas também aumenta o overhead.

Enquadramento

Enquadrar significa definir claramente onde um quadro começa e termina.

Sem enquadramento:

0111111001000001010000100111111001111110...
Reflita

Se o receptor vê apenas um fluxo contínuo, como ele sabe onde termina um quadro e começa o próximo?

Métodos de enquadramento

MétodoVantagemLimitação
Contagem de caracteresSimplesErro no tamanho desalinhar tudo
Bytes de flag + stuffingIntuitivoPrecisa escapar bytes especiais
Flags + bit stuffingBom para protocolos orientados a bitsExige processamento bit a bit
Violação de codificaçãoEleganteDepende da camada física

Contagem de caracteres

Exemplo:

[Tamanho = 5][A][B][C][D][E]

Se o campo de tamanho estiver correto, o receptor sabe quantos bytes ler.

Problema: se o próprio campo de tamanho for corrompido, a leitura do fluxo perde sincronização.

Byte stuffing

Usamos um byte especial FLAG para marcar início e fim do quadro.

Problema:

[FLAG][A][FLAG][B][FLAG]

O FLAG do meio pode ser confundido com fim do quadro.

Solução: introduzir ESC.

Byte stuffing em ação

Original:  [A][FLAG][B]
Na rede:   [FLAG][A][ESC][FLAG][B][FLAG]

flowchart TD
    O["Original<br/>4f 6c 61 20 7e 20 4d 75 6e 64 6f"]
    S["Byte stuffing<br/>7e interno vira 7d 7e"]
    N["Na rede<br/>7e 4f 6c 61 20 7d 7e 20 4d 75 6e 64 6f 7e"]

    O --> S --> N

Bit stuffing

Quando a flag é um padrão de bits, como 01111110, usamos outra estratégia.

Regra:

  • sempre que aparecem cinco 1 seguidos nos dados;
  • o transmissor insere um 0;
  • o receptor remove esse 0 na recepção.

Estrutura de um quadro

flowchart LR
    H["Cabeçalho<br/>controle"]
    D["Payload<br/>dados da camada superior"]
    T["Trailer<br/>CRC / verificação"]

    H --> D --> T
Intuição

O cabeçalho orienta a interpretação do quadro. O trailer normalmente carrega a verificação de integridade.

Erros no enlace

Em um meio real, os bits podem mudar por:

  • ruído elétrico;
  • interferência;
  • falhas de hardware;
  • erros em rajada.
Padrão real de erro

Em redes reais, muitos erros aparecem em rajadas, e não como um único bit isolado.

Detectar não é corrigir

Palavra-chave

O segredo desses mecanismos é a redundância.

Código de Hamming

O código de Hamming mostra que é possível localizar um erro de 1 bit usando bits de verificação em posições estratégicas.

Exemplo: Hamming (7,4)

  • 4 bits de dados
  • 3 bits de verificação
  • 7 bits no total

Hamming (7,4) passo a passo

Dados a transmitir:

1011

Posições do quadro:

Posição1234567
Tipop1p2d1p4d2d3d4
Valorp1p21p4011

Critério dos grupos de Hamming

O padrão vem do binário da posição.

PosiçãoBinário
1001
2010
3011
4100
5101
6110
7111
  • p1 olha posições cujo último bit é 1
  • p2 olha posições cujo bit do meio é 1
  • p4 olha posições cujo primeiro bit é 1

Calculando p1, p2 e p4

Se usarmos paridade par:

  • p1 cobre 1, 3, 5, 7
  • p2 cobre 2, 3, 6, 7
  • p4 cobre 4, 5, 6, 7

Resultado:

p1 = 0
p2 = 1
p4 = 0

Palavra final:

0110011

Como a síndrome aponta o erro

Se o receptor receber:

0110111

e as verificações derem:

p1 falha -> 1
p2 passa -> 0
p4 falha -> 1

Então:

p4 p2 p1 = 1 0 1 = 101₂ = 5
Resultado

A síndrome aponta diretamente para a posição 5 como bit defeituoso.

Controle de fluxo

Mesmo sem ruído, ainda existe um problema: o transmissor pode ser mais rápido que o receptor.

Atenção conceitual
Controle de fluxo não é congestionamento. Fluxo trata do ritmo entre emissor e receptor. Congestionamento trata da rede como um todo.

Protocolos básicos de enlace

O Tanenbaum apresenta uma evolução didática:

  • simplex sem restrições: tudo é perfeito;
  • stop-and-wait sem erro: agora o receptor precisa controlar o ritmo;
  • stop-and-wait com ruído: entram ACK, timeout e número de sequência.

Stop-and-wait

Ideia central:

  1. envia um quadro;
  2. espera a confirmação;
  3. só então envia o próximo.

Isso resolve o problema do receptor lento, mas ainda não resolve perda de quadros nem perda de ACKs.

ACK perdido

sequenceDiagram
    participant A as Emissor A
    participant B as Receptor B

    A->>B: Quadro 0
    B->>B: Entrega à camada superior
    B-->>A: ACK 0
    Note over A,B: ACK se perde no caminho
    A->>A: Timeout
    A->>B: Retransmite Quadro 0
    B->>B: Detecta duplicata pelo número de sequência
Problema central

Se o ACK se perde, como evitar que o mesmo quadro seja entregue duas vezes?

Número de sequência

No stop-and-wait, basta 1 bit:

flowchart LR
    Q0["Quadro 0"] --> Q1["Quadro 1"] --> Q0b["Quadro 0"] --> Q1b["Quadro 1"]

Se o receptor esperava 1 e recebeu 0, ele sabe que recebeu uma duplicata.

Demonstração prática no terminal

Três comandos simples já deixam a aula mais concreta:

printf 'Ola ~ Mundo\n' | xxd -g 1
printf 'Ola Mundo' | cksum
printf 'Ola Mund0' | cksum
  • xxd -g 1 mostra os bytes reais da mensagem;
  • o ~ aparece como 0x7e, valor clássico de FLAG;
  • cksum mostra como pequenas mudanças alteram o valor de verificação.
